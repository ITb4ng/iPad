# 릴리즈 전 검수 문서 구조 정리 및 기준 최신화

> **작업 브랜치:** `dev`  
> **관련 커밋:** `f41bb5a`

---

## 작업 개요

이 날 작업은 코드 변경보다 **릴리즈 브랜치 생성 직전의 판단 근거를 문서로 명확하게 남기는 일**에 가까웠다.

핵심 흐름은 아래와 같았다.

- CSS 리팩토링 QA 문서 재정리
- 링크 / 버튼 마크업 정책 문서 보강
- 릴리즈 전 dev 통합 상태를 검수 기록 관점으로 재작성
- 날짜별 작업 기록 일부 최신화

---

## 커밋 기준 작업 내역

### 1. `f41bb5a`
`docs: CSS QA, 링크 정책, 릴리즈 전 검수 문서 최신화`

#### 주요 작업 내용

- `docs/qa/css-refactor-qa.md`
  - CSS 파일을 왜 분리했는지, `main.css / header.css / footer.css`의 역할이 무엇인지 다시 정리했다.
  - 유지보수성, 탐색 비용, cascade 충돌, header / mobile panel / detail section 리스크 기준으로 QA 문서를 구조화했다.
  - 체크리스트를 `Pass / Pending / Need Review` 상태표로 보강했다.

- `docs/policies/link-button-policy.md`
  - “이동은 `a`, 상태 제어는 `button`” 원칙을 기준으로 현재 프로젝트가 요구사항을 만족하는지 검수표를 추가했다.
  - 헤더, 제품 내비게이션, 본문 CTA, 푸터, 404 흐름을 각각 표로 점검할 수 있게 정리했다.
  - 금지 패턴(`href="#"`, `javascript:void(0)`, 클릭용 `div/span`) 점검 기준을 문서에 반영했다.

- `docs/release/release.md`
  - 문서 성격을 단순 배포 준비 안내가 아니라 “dev 통합 검수 기록”으로 다시 정리했다.
  - `feat/portfolio-polish`, `chore/ipad-final-polish`, 마지막 자산 보정 커밋까지 포함해, 무엇이 통합되었고 왜 중요한지 서술했다.
  - 릴리즈 브랜치 생성 가능 여부와 남은 검증 항목, Netlify 배포 전 확인 항목을 문서화했다.

- `docs/work/2026-04-27.md`
  - 기존 날짜 문서도 현재 문서 흐름과 어긋나지 않도록 일부 최신화했다.

#### 왜 이 작업이 필요했는가

- dev 브랜치가 기능 개발 브랜치인지, 릴리즈 후보 통합 브랜치인지 문서상으로 분리되어 보이지 않으면 릴리즈 판단이 흔들린다.
- 최근 작업은 단순 기능 추가보다 구조 정리와 검수 기준 정리에 가까웠기 때문에, 코드보다 문서가 먼저 “현재 상태”를 설명할 수 있어야 했다.
- 나중에 release 브랜치를 기준으로 회귀 검수를 진행할 때도, 어떤 항목이 이미 충족되었고 무엇이 남았는지 문서에서 바로 읽혀야 했다.

- 릴리즈 브랜치 생성 전 기준 문서가 사실상 한 번 정리된 상태가 되었다.

## 인사이트 및 회고

- 릴리즈 직전 문서는 작업 이력보다 판단 근거를 남기는 역할이 더 중요하다.
- 같은 코드라도 문서가 없으면 “완료”와 “검증 대기”를 분리하기 어렵고, 릴리즈 브랜치의 목적도 흐려진다.
- 특히 CSS 리팩토링이나 링크 정책처럼 결과가 여러 화면에 흩어지는 작업은, 코드보다 문서가 먼저 전체 맥락을 잡아줘야 한다.
