## 1. 문제

이 프로젝트는 단순한 정적 랜딩 페이지가 아니라, 상품 탐색과 구매 전환 흐름을 함께 다루는 포트폴리오형 리빌드 페이지다.

처음에는 클론 코딩 성격에서 출발했지만, 최종 릴리즈 단계에서는 단순히 원본 화면을 비슷하게 재현하는 것보다 사용자가 어떤 흐름으로 탐색하고, 어떤 요소를 조작하며, 어떤 경로로 이동하는지를 설명할 수 있는 프로젝트로 정리하는 것을 목표로 했다.

실제 서비스가 존재하는 페이지를 포트폴리오 프로젝트로 재구성할 때는 링크와 버튼의 역할을 명확히 구분하는 정책이 필요하다고 판단했다.

시각적으로는 모두 CTA처럼 보이더라도, 사용자를 다른 위치로 이동시키는 요소인지, 현재 화면의 상태만 변경하는 요소인지에 따라 마크업이 달라져야 한다. 이 기준이 없으면 `javascript:void(0)`, `href="#"`, 클릭 가능한 `div`나 `span`처럼 동작은 하지만 의미가 불명확한 패턴이 늘어날 수 있다.

따라서 이 문서는 단순히 태그 사용 규칙을 정리하기 위한 문서가 아니라, 프로젝트 전체의 탐색 흐름과 사용자 경험을 일관되게 유지하기 위한 검수 기준이다.

## 2. 판단 기준

핵심 원칙은 단순하다.

- 이동은 `<a>`
- 상태 제어는 `<button>`

이 원칙을 지키는 이유는 접근성 때문만이 아니라, 현재 `dev` 브랜치의 콘텐츠 흐름을 설명 가능하게 만들기 위해서다.

헤더, 제품 내비게이션, 본문 CTA, 푸터, 404 흐름이 같은 원칙을 따라야 사용자는 “왜 이 요소를 눌렀을 때 페이지가 바뀌는지” 또는 “왜 현재 화면 안에서 패널만 열리는지”를 예측할 수 있다.

즉, 이 프로젝트에서는 단순히 클릭되게 만드는 것보다 사용자가 클릭 전에 결과를 예측할 수 있는 구조를 우선했다.

| 질문 | 의미 | 권장 마크업 |
| --- | --- | --- |
| 클릭하면 위치가 바뀌는가 | 목적지가 있는 이동이다. | `<a>` |
| 같은 페이지의 특정 섹션으로 이동하는가 | 내부 앵커 이동이다. | `<a>` |
| 외부 서비스나 정책 문서로 이동하는가 | 목적지가 있는 외부 이동이다. | `<a>` |
| 현재 페이지 상태만 바꾸는가 | 패널 열기, 토글, 닫기, 재생/정지 같은 상태 제어다. | `<button>` |
| 브라우저 상태를 제어하는가 | 이전 페이지 복귀처럼 현재 환경의 동작을 제어한다. | `<button>` |
| 실제 페이지가 존재하지 않는가 | 빈 링크로 방치하지 않고 404, 비활성, 대체 흐름을 검토한다. | 상황별 판단 |

## 3. 프로젝트 관점에서의 판단

이 프로젝트는 Apple iPad 페이지를 참고한 리빌드 프로젝트이지만, 원본 서비스를 무분별하게 따라 하는 것을 목표로 하지 않았다.

원본 서비스가 가진 시각적 완성도, CTA 구조, 탐색 흐름은 참고하되, 현재 프로젝트 안에서 직접 설계하고 구현한 섹션, 인터랙션, 접근성 처리, 배포 흐름을 명확히 보여주는 것이 더 중요하다고 판단했다.

특히 실서비스가 존재하는 클론형 프로젝트에서는 외부 링크를 어떻게 다룰지가 중요하다.

모든 링크를 원본 서비스로 연결하면 사용자는 프로젝트 내부에서 설계한 흐름을 충분히 경험하기 전에 외부 서비스로 이탈할 수 있다. 반대로 모든 외부 링크를 제거하면 구매 전환, 상세 정보, 정책 문서처럼 실제 서비스 문맥이 필요한 흐름을 설명하기 어렵다.

따라서 이 프로젝트에서는 외부 Apple 링크를 무조건 제거하지 않고, 아래 기준에 따라 유지 여부를 판단했다.

- 정보 보강이 필요한가
- 구매 전환 흐름이 명확한가
- 정책, 지원, 계정, 주문처럼 사용자 기대가 분명한가
- 프로젝트 내부에서 이미 충분히 설명 가능한 내용인가
- 외부 이동이 본문 탐색 흐름을 방해하는가
- 실제 존재하지 않는 경로를 무의미한 클릭 요소로 남기고 있지는 않은가

이 기준을 통해 링크는 단순한 이동 수단이 아니라, 사용자 흐름을 설계하는 장치로 다뤘다.

## 4. 개인 판단과 설계 의도

기존 클론 코딩 강의에서 시작한 프로젝트라도, 최종 포트폴리오 단계에서는 단순히 화면을 따라 만든 결과물만으로는 충분하지 않다고 판단했다.

화려한 UI, 체계적인 컨벤션, 접근성, 사용자 경험은 모두 중요하다. 하지만 실제 서비스가 존재하는 프로젝트를 리빌드할 때는 사용자가 어떤 요소를 눌렀을 때 어디로 이동하고, 어떤 요소를 눌렀을 때 현재 화면의 상태만 바뀌는지 명확히 설계하는 것이 특히 중요하다고 느꼈다.

이 프로젝트에서 링크 / 버튼 마크업 정책을 문서화한 이유는 단순히 문법적으로 올바른 태그를 쓰기 위해서가 아니다. 프로젝트 안에서 사용자 흐름의 위계질서를 확립하고, 클릭 가능한 요소가 어떤 의미를 가지는지 설명할 수 있는 구조를 만들기 위해서다.

실서비스가 존재하는 클론형 페이지에서 모든 CTA를 외부 원본 서비스로 연결하면 사용자는 내가 만든 프로젝트의 흐름을 충분히 경험하기 전에 외부로 이동하게 된다. 이 경우 사용자는 다시 프로젝트로 돌아오기 위해 브라우저 뒤로 가기나 재진입 같은 불필요한 동작을 해야 한다.

따라서 이 프로젝트에서는 사용자가 가능한 한 프로젝트 내부에서 내가 직접 설계한 섹션, 인터랙션, 콘텐츠 흐름을 먼저 경험할 수 있도록 했다. 외부 Apple 링크는 필요한 경우에만 유지하고, 프로젝트 내부에서 설명 가능한 내용은 내부 흐름으로 대체하거나 섹션 이동으로 정리했다.

반대로 실제 서비스 문맥이 필요한 영역은 외부 링크를 유지했다. 구매 전환, 상세 정보 보강, 정책 / 지원 / 계정 / 주문 같은 흐름은 사용자가 실제 서비스로 이동할 것이라고 예측할 수 있는 영역이기 때문이다.

즉, 외부 링크를 무조건 제거하는 것이 목적이 아니라, 외부 이동이 필요한 이유를 설명할 수 있는 경우에만 유지하는 것이 목적이다.

또한 실제 동작하지 않는 링크나 존재하지 않는 페이지는 `javascript:void(0)` 또는 `href="#"`로 임시 처리하지 않도록 했다. 이런 방식은 마우스나 터치로 상호작용했을 때 사용자가 예측하기 어려운 결과를 만들고, 프로젝트의 완성도를 낮출 수 있다.

따라서 실제 페이지가 존재하지 않는 경우에는 404 페이지 흐름, 비활성 상태, 내부 섹션 대체, 외부 Apple 링크 유지 중 하나를 선택하도록 기준을 세웠다.

이 정책의 목적은 사용자의 불필요한 클릭과 이탈을 줄이고, 프로젝트 안에서 설계한 탐색 흐름을 명확히 경험하게 만드는 것이다. 동시에 릴리즈 단계에서 링크 의미, 버튼 역할, 실패 경로, 정적 배포 환경의 라우팅 리스크까지 함께 점검하기 위한 기준이기도 하다.

## 6. 링크 `<a>` 사용 기준

링크는 사용자를 특정 목적지로 이동시키는 요소에 사용한다.

| 사용 위치 | 판단 기준 |
| --- | --- |
| 내부 섹션 이동 | 현재 페이지 안의 특정 섹션으로 이동하는 경우 |
| 내부 페이지 이동 | 프로젝트 안의 다른 페이지로 이동하는 경우 |
| 외부 페이지 이동 | Apple 상세 정보, 구매, 지원, 정책 등 실제 목적지가 있는 경우 |
| 전화 연결 | `tel:`처럼 명확한 사용자 행동 목적이 있는 경우 |
| 404 복귀 링크 | 홈 또는 특정 섹션으로 이동하는 경우 |

예시:

    <a href="#compare">모델 비교하기</a>
    <a href="/buy">구입하기</a>
    <a href="/learn/accessibility">손쉬운 사용 더 알아보기</a>
    <a href="tel:080-000-0000">전화 문의</a>

## 7. 버튼 `<button>` 사용 기준

버튼은 현재 페이지 안에서 상태를 변경하거나 UI를 제어하는 요소에 사용한다.

| 사용 위치 | 판단 기준 |
| --- | --- |
| 검색 패널 | 현재 화면 안에서 검색 영역을 열고 닫는 상태 제어 |
| 장바구니 패널 | 현재 화면 안에서 장바구니 영역을 열고 닫는 상태 제어 |
| 모바일 메뉴 | 메뉴 패널 열기/닫기 |
| 푸터 아코디언 | 하위 목록 펼침/접힘 |
| 비디오 컨트롤 | 재생, 정지, 음소거 등 미디어 상태 제어 |
| 404 이전 페이지 복귀 | 브라우저의 `history.back()`을 실행하는 상태 제어 |

예시:

    <button type="button" aria-expanded="false" aria-controls="search-panel">
      검색
    </button>

    <button type="button" data-error-back>
      이전 페이지로 돌아가기
    </button>

## 8. 외부 Apple 링크 유지 기준

외부 Apple 링크는 “무조건 제거” 대상이 아니다.

현재 프로젝트 내부에서 충분히 설명하지 않는 정보를 보강하거나, 구매 전환과 정책 목적이 분명할 때는 유지 가능하다.

| 유지 가능 기준 | 설명 | 현재 예시 |
| --- | --- | --- |
| 정보 보강 | 프로젝트 내부에 없는 상세 정보나 보조 설명을 연결할 때 | `/learn/cellular`, `/learn/ipados`, `/learn/accessibility` |
| 구매 전환 | 구매 또는 구매 직전 흐름이 명확할 때 | `/buy`, `/shop/accessories`, `/trade-in` |
| 정책 / 지원 | 법적 고지, 지원, 계정, 주문처럼 사용자 기대가 명확할 때 | `/legal/*`, `/support/*`, `/account`, `/orders` |

반대로 아래 기준에 해당하는 링크는 줄이거나 대체를 검토한다.

| 줄이거나 대체를 검토할 기준 | 설명 |
| --- | --- |
| 단순 복제 목적 링크 | 현재 프로젝트가 이미 제공하는 내용을 다시 외부로 보내는 경우 |
| 과도한 이탈 유도 | 본문 흐름보다 외부 이동을 먼저 강하게 요구하는 경우 |
| 목적 불명확 CTA | 정보 보강인지 구매 전환인지 설명하기 어려운 경우 |
| 존재하지 않는 경로 | 실제 페이지가 없고, 사용자에게 의미 있는 결과를 제공하지 못하는 경우 |

## 9. 존재하지 않는 링크 처리 기준

실제 페이지가 존재하지 않는 경로는 `href="#"`나 `javascript:void(0)`으로 임시 처리하지 않는다.

정적 포트폴리오 프로젝트에서는 모든 원본 서비스 경로를 구현하기 어렵기 때문에, 존재하지 않는 경로에 대해서는 아래 기준 중 하나를 선택한다.

| 처리 방식 | 사용 기준 |
| --- | --- |
| 404 페이지 연결 | 사용자가 잘못된 경로에 진입했을 때 복귀 흐름을 제공할 수 있는 경우 |
| 비활성 상태 처리 | 아직 구현하지 않은 기능임을 명확히 보여줘야 하는 경우 |
| 내부 섹션 대체 | 외부 이동보다 프로젝트 안의 설명 섹션으로 유도하는 것이 적절한 경우 |
| 외부 Apple 링크 유지 | 실제 서비스 문맥이 필요하고 목적지가 명확한 경우 |

이 기준은 사용자가 클릭했을 때 아무 반응이 없거나, 예측하기 어려운 결과를 경험하지 않도록 하기 위한 조치다.

## 10. 비활성 요소 처리 기준

아직 구현하지 않은 기능이나 실제 목적지가 없는 요소는 일반 CTA처럼 보이게 두지 않는다.

비활성 요소는 사용자가 클릭 가능한 링크나 버튼으로 오해하지 않도록 시각적, 의미적 처리를 함께 고려한다.

| 처리 기준 | 설명 |
| --- | --- |
| 시각적 구분 | 일반 CTA보다 약한 색상, 낮은 대비, 비활성 커서 등으로 구분한다. |
| 의미 전달 | 필요한 경우 “준비 중”, “현재 페이지에서 제공하지 않음” 같은 설명을 제공한다. |
| 키보드 접근 제어 | 실제 동작하지 않는 요소가 불필요하게 Tab 흐름에 포함되지 않도록 검토한다. |
| 마우스 / 터치 동작 제어 | 클릭 가능한 것처럼 보이지만 아무 동작도 하지 않는 상태를 피한다. |

단, 비활성 요소를 남발하면 사용자 경험이 떨어질 수 있으므로, 가능하면 내부 섹션 이동이나 404 복귀 흐름으로 대체하는 것을 우선한다.

---

## 11. 404 페이지 흐름 기준

404 페이지는 사용자가 잘못된 경로에 진입했을 때 프로젝트 내부 흐름으로 복귀할 수 있도록 설계한다.

| 요소 | 권장 마크업 | 판단 |
| --- | --- | --- |
| 홈으로 돌아가기 | `<a>` | 명확한 목적지가 있는 이동이다. |
| 주요 섹션으로 돌아가기 | `<a>` | 특정 섹션으로 이동하는 목적지가 있다. |
| 이전 페이지로 돌아가기 | `<button>` | 브라우저의 이전 기록을 제어하는 동작이다. |

예시:

    <a href="/" data-error-home>
      홈으로 돌아가기
    </a>

    <a href="/#compare" data-error-home-section>
      모델 비교 섹션으로 이동
    </a>

    <button type="button" data-error-back>
      이전 페이지로 돌아가기
    </button>

`history.back()`은 referrer가 없는 직접 진입 상황에서는 사용자가 기대한 대로 동작하지 않을 수 있다. 따라서 이전 페이지 복귀 버튼은 홈 이동 fallback과 함께 검토한다.

## 16. 릴리즈 전 확인 명령어

아래 검색을 통해 금지 패턴이 다시 유입되지 않았는지 확인한다.

    grep -R "javascript:void(0)" index.html 404.html js styles
    grep -R "href=\"#\"" index.html 404.html js styles
    grep -R "role=\"button\"" index.html 404.html js styles

클릭 가능한 비의미 요소가 있는지도 함께 확인한다.

    grep -R "onclick" index.html 404.html js styles
    grep -R "data-.*click" index.html 404.html js styles

단, `onclick` 또는 `data-*` 검색 결과가 있다고 해서 무조건 문제가 되는 것은 아니다. 실제로 사용자 조작 요소가 `<button>` 또는 `<a>`와 연결되어 있는지 함께 확인해야 한다.

## 18. 결론

현재 `dev` 브랜치의 링크 / 버튼 마크업은 요구사항 기준을 대체로 충족한다.

핵심 원칙인 “이동은 `<a>`, 상태 제어는 `<button>`”은 헤더, 제품 내비게이션, 본문 CTA, 푸터, 404 흐름에서 일관되게 유지되고 있다.

이번 정책 정리는 단순히 태그를 올바르게 쓰기 위한 작업이 아니라, 실제 서비스형 페이지를 포트폴리오 프로젝트로 리빌드할 때 사용자의 탐색 흐름을 어떻게 설계하고 통제할 것인지에 대한 기준을 남기기 위한 작업이다.

특히 외부 Apple 링크는 무조건 제거하지 않고, 정보 보강 · 구매 전환 · 정책 / 지원처럼 목적이 분명한 경우에만 유지했다. 반대로 목적이 불명확하거나 프로젝트 내부 흐름을 방해할 수 있는 링크는 줄이거나 대체를 검토했다.

또한 실제 동작하지 않는 링크를 `javascript:void(0)`이나 `href="#"`로 방치하지 않고, 404 페이지, 비활성 상태, 내부 섹션 이동, 외부 링크 유지 중 어떤 방식이 사용자에게 가장 예측 가능한지 기준을 세웠다.

남은 과제는 태그 선택 자체가 아니라, 정적 배포 환경에서 `/buy`, `/compare`, `/learn/*` 같은 경로가 의도한 방식으로 처리되는지 확인하는 일이다. 따라서 릴리즈 전에는 Netlify 배포 환경에서 alias, fallback, 404 복귀 흐름을 함께 검증해야 한다.

이 기준을 통해 프로젝트는 단순 클론 화면이 아니라, 링크 의미, 버튼 역할, 외부 이동 기준, 실패 경로, 정적 배포 리스크까지 고려한 서비스형 랜딩 페이지 리빌드로 정리된다.
