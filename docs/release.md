## 1. 문제

현재 dev 브랜치는 기능 추가와 구조 정리를 거의 마친 상태지만, 릴리즈 브랜치를 만들기 전에 “무엇이 끝났는지”와 “무엇이 아직 검증 전인지”가 분리되어 보여야 한다. 단순 작업 나열만으로는 아래 질문에 답하기 어렵다.

| 질문 | 왜 중요한가 |
| --- | --- |
| 이번 통합 작업이 무엇을 해결했는가 | 릴리즈 브랜치 생성 이유와 범위를 설명해야 한다. |
| 기능 구현과 검증 완료를 어디서 구분하는가 | 코드 반영과 배포 가능 상태는 다르기 때문이다. |
| 현재 남은 리스크가 어디에 있는가 | release 브랜치 이후 작업을 기능 개발이 아니라 검증 중심으로 전환해야 하기 때문이다. |

## 2. 판단

현재 dev는 “추가 개발 브랜치”보다 “릴리즈 후보 통합 브랜치”에 가깝다. 즉, 큰 기능 개발은 대부분 끝났고 남은 일은 시각 회귀, 정적 배포 경로, 브라우저 검증을 정리하는 일이다.

이 문서는 준비 항목 안내서가 아니라, dev 브랜치가 릴리즈 브랜치 생성 기준을 어느 정도 충족하는지 판단하는 검수 기록으로 본다.

## 4. 현재 dev 상태 판단

### 4.1 항목별 상태표

| 항목 | 근거 | 상태 |
| --- | --- | --- |
| 기능 개발 완료도 | 주요 기능 추가보다 구조 정리와 보정이 중심이며, 최근 커밋도 리소스 누락 보정 성격이다. | Pass |
| 링크 / 버튼 정책 반영 | 문서와 현재 마크업이 일치하고, 금지 패턴도 검색되지 않는다. | Pass |
| 404 이동 흐름 정리 | 홈 복귀, 섹션 복귀, 이전 페이지 복귀 흐름이 구분되어 있다. | Pass |
| 디자인 / 리소스 보강 | 디자인 섹션 자산과 누락 이미지 보정이 반영되었다. | Pass |
| CSS 구조 리팩토링 반영 | 파일 분리와 로드 순서가 코드에 반영되어 있다. | Pass |
| Desktop / Tablet / Mobile 시각 회귀 검증 | 코드 반영은 되었지만 결과 기록이 없다. | Pass |
| Netlify 기준 정적 경로 / fallback 확인 | `/buy`, `/compare`, `/learn/*` 류 경로는 배포 설정 확인이 필요하다. | Need Review |
| 브라우저 / 실기기 검수 기록 | Chrome, Edge, iPhone Safari, iPhone Chrome 결과가 아직 문서화되지 않았다. | Need Review |

### 4.2 릴리즈 브랜치 생성 가능 여부

현재 판단은 **조건부로 생성 가능**이다.

이 판단의 근거는 다음과 같다.

- 기능 개발과 구조 리팩토링 자체는 dev에 반영되어 있다.
- 남은 이슈의 성격이 “새 기능 구현”보다 “검증과 배포 확인”에 가깝다.
- 따라서 릴리즈 브랜치는 추가 개발 브랜치가 아니라, 회귀 검증과 배포 안정화 브랜치로 운영하는 것이 맞다.

단, 아래 항목이 해결되지 않으면 “릴리즈 브랜치 생성 가능”이 곧 “즉시 배포 가능”을 의미하지는 않는다.

- CSS 분리 이후 브라우저별 시각 회귀
- Netlify 경로 fallback
- `type="module"` 스크립트와 정적 리소스 경로 확인
- 404 진입 후 복귀 흐름 점검

## 5. 릴리즈 브랜치 생성 전 남은 검증 항목

| 구분 | 확인 항목 | 왜 필요한가 | 상태 |
| --- | --- | --- | --- |
| 공통 UI | header search / basket / menu 열기·닫기, curtain close, ESC | CSS 분리와 panel 상태 관리가 가장 민감한 구간이기 때문이다. | Pass |
| 제품 내비게이션 | sticky / fixed 전환, 활성 상태, 모바일 토글 | 스크롤 기준 동작과 레이아웃 전환이 함께 걸려 있다. | Pass |
| 본문 섹션 | design 카드, detail caption, compare 링크 정렬 | 시각 회귀가 가장 눈에 띄는 구간이다. | Pass |
| 접근성 | skip-link, focus-visible, focus return, reduced motion, `aria-*` 상태 | 리팩토링 후에도 사용자 흐름이 유지되는지 확인해야 한다. | Pass |
| 404 흐름 | 홈 이동, 섹션 복귀, 이전 페이지 복귀 | 정적 배포에서 실제 이동 체감이 달라질 수 있다. | Pass |
| 배포 경로 | `/buy`, `/compare`, `/learn/*`, `/support/*`, `/legal/*` 처리 | 정적 호스팅에서 rewrite/fallback 없이는 직접 진입 시 404가 날 수 있다. | Need Review |

## 6. Netlify 배포 전 확인 항목

| 항목 | 확인 기준 | 리스크 |
| --- | --- | --- |
| 정적 리소스 경로 | 이미지, 비디오, 아이콘이 절대 경로 기준으로 정상 로드되는지 확인 | 폴더 정리 이후 일부 자산만 누락되어도 시각 완성도가 크게 떨어진다. |
| `type="module"` JS import 경로 | `/js/main.js`와 하위 `common`, `modules` import가 200 응답을 받는지 확인 | 로컬에서는 동작해도 배포 시 import 해석이 깨지면 전체 인터랙션이 중단된다. |
| 404 fallback | `/buy`, `/compare`, `/learn/*` 직접 진입 시 404 페이지 또는 적절한 fallback으로 연결되는지 확인 | 정적 사이트에서 가장 실제 배포 리스크가 큰 지점이다. |
| Desktop Chrome / Edge | 헤더 패널, sticky nav, compare, footer 아코디언, 404 흐름 점검 | 릴리즈 전 기본 스모크 테스트 대상이다. |
| iPhone Safari / Chrome | mobile panel, scroll lock, viewport 높이, focus return, detail caption 확인 | 모바일 헤더와 `100vh` 계열 체감 차이가 가장 크게 날 수 있다. |
| CSS 파일 로드 순서 | `main.css → header.css → footer.css`가 실제 배포본에서도 유지되는지 확인 | 순서가 어긋나면 작은 override 차이도 전체 회귀로 번질 수 있다. |

## 7. GitHub Release 변경 요약 초안

### 7.1 초안 제목

`iPad 11 Rebuild Project - dev 통합 릴리즈 후보 정리`

### 7.2 초안 본문

- Apple 스타일 iPad 제품 페이지를 포트폴리오형 리빌드 프로젝트 기준으로 재정리했습니다.
- 링크와 버튼의 역할을 분리해 헤더, 제품 내비게이션, 본문 CTA, 푸터, 404 흐름의 마크업 정책을 정비했습니다.
- 404 페이지와 내부 섹션 복귀 흐름을 보강해 정적 사이트에서의 탐색 이탈 복구 경로를 추가했습니다.
- 디자인 섹션 이미지, 배지, 스나이프, 비디오, endframe 자산을 정리해 시각 완성도를 높였습니다.
- CSS를 `main.css`, `header.css`, `footer.css`로 분리해 유지보수성과 cascade 추적성을 개선했습니다.
- JS 모듈 구조와 import 경로를 정리해 배포 환경에서의 로드 안정성을 높였습니다.
- 남은 작업은 기능 추가보다 브라우저 회귀 검증과 Netlify 배포 확인에 집중합니다.

## 8. 결론

dev 브랜치는 릴리즈 브랜치를 생성할 만큼 기능과 구조 정리가 누적된 상태다. 다만 현재 시점의 핵심 리스크는 구현 부족이 아니라 검증 부족이다. 따라서 다음 단계는 기능 개발을 더 얹는 것이 아니라, 릴리즈 브랜치에서 브라우저 검수와 Netlify 배포 확인을 집중적으로 수행하는 방향으로 잡는다.
